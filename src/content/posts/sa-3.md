## 二、逐题解析

### 第1题　编译器四阶段的架构风格 ✅

**题干**：某公司拟为某种新型可编程机器人开发相应的编译器。该编译过程包括词法分析、语法分析、语义分析和代码生成四个阶段，每个阶段产生的结果作为下一个阶段的输入，且需独立存储。针对以上描述，该集成开发环境应采用（　）架构风格最为合适。
**选项**：A. 管道-过滤器　B. 主程序-子程序　C. 解释器　D. 仓库
**标准答案：A**

- **A ✅ 管道-过滤器**。四个阶段天然构成一条**线性数据流**：词法分析产出的记号流 → 语法分析产出的语法树 → 语义分析产出的中间表示 → 代码生成产出的目标代码。每个阶段都是一个**独立、可替换的过滤器**，阶段间的数据通道就是**管道**。“每个阶段结果独立存储”正是过滤器**不共享状态、各自持有中间结果**的特征，因此风格判定仍是管道-过滤器。
- **B ❌ 主程序-子程序**。该风格是“调用-返回”结构，数据通过**参数/全局变量**在过程间传递，控制权集中于主程序，各阶段不是并列的数据变换节点。编译器虽也可用这种结构实现，但题干强调“前一阶段输出作为后一阶段输入”的**流水线拓扑**，“最合适”取管道-过滤器。
- **C ❌ 解释器**。解释器属于**虚拟机风格**（解释引擎 + 被解释的程序/数据），特征是**边解释边执行**、不生成目标代码；题干的编译器是“分析 + 生成目标代码”，不是解释执行。
- **D ❌ 仓库**。仓库风格的核心是**中央数据结构 + 多个独立构件围绕它读写**（互相之间不直接通信），典型如数据库、黑板、IDE 的信息库。本题数据是**单向逐级流动**、由各阶段分别存储，没有“共享中央数据被多个构件并发访问”的结构，因此不是仓库。

**知识点**

1. 管道-过滤器风格的三要素：**过滤器**（独立处理步骤，输入流→输出流）、**管道**（连接件，单向数据流，可缓冲）、**数据**（流式）。
2. 优点：过滤器可独立理解、重用、替换；支持**并发/流水线**执行（各阶段可并行）；便于增加新过滤器（可扩展）；可做吞吐量分析。
3. 缺点：不适合**交互式**应用（用户事件难以建模成数据流）；数据格式需上下游**协商一致**（格式转换开销）；**批处理**特性导致响应延迟；错误处理与状态共享困难。
4. 典型实例：Unix shell 管道 `grep | sort | uniq`、**编译器**、信号/图像处理流水线、ETL 数据加工。

**教材关联**：第 3 章 §3.1.1 管道与过滤器（教材以“编译器”“Unix 管道”为标准例子，并给出该风格的优缺点表）。

### 第2题　按注册兴趣推送新闻 ✅

**题干**：某公司拟开发一个新闻系统，该系统可根据用户的注册兴趣，向用户推送其感兴趣的新闻内容，该系统应采用（　）架构风格最为合适。
**选项**：A. 黑板　B. 管道-过滤器　C. 主程序-子程序　D. 事件驱动系统
**标准答案：D**

- **D ✅ 事件驱动系统（隐式调用）**。“用户订阅兴趣、系统按兴趣推送”就是典型的**发布-订阅**：新闻发布者不直接调用任何用户程序，而是**发布事件**（“有新新闻”），订阅了该兴趣的用户接收端被**隐式调用**完成推送。构件之间通过事件间接通信，新增用户/新增兴趣类型都无需修改发布者 → 耦合度最低、可扩展性最好，正好匹配“内容源不断变化、用户数量动态增长”的新闻系统。
- **A ❌ 黑板**。黑板要求**多个知识源围绕同一块共享数据结构协作求解**，并由**控制构件**调度“谁在什么条件下写黑板”。推送系统既没有共享求解空间，也没有集中的推理调度，判定不成立。
- **B ❌ 管道-过滤器**。管道是**线性、单向**的数据变换，一批输入对应一批输出；而推送是**异步、一对多、按事件触发**的，拓扑与管道不符。
- **C ❌ 主程序-子程序**。该风格是同步调用、调用者必须等待返回；推送是异步且接收方数量不确定，用同步调用实现会导致发布者与所有接收者强耦合，难以扩展。

**知识点**

1. 隐式调用的定义（教材原句）：构件**不直接调用**一个过程，而是**触发或广播**一个或多个事件；其他构件通过**注册/订阅**声明对哪些事件感兴趣，由**事件机制**负责分发（第 14 题即此定义的判断题）。
2. 优点：松耦合、易演化（可插入新构件而不改旧构件）、支持异步并发、构件可独立部署。
3. 缺点：**控制流难以理解与推理**（谁在何时被调用不直观）、**不能保证响应顺序与结果正确性**、事件语义（什么算一个事件）缺乏统一标准、调试与测试困难。
4. 常见实现：观察者模式、消息队列/消息中间件（Kafka、RabbitMQ）、GUI 事件循环、微服务间的事件总线。

**教材关联**：第 3 章 §3.1.3 基于事件的系统（隐式调用）；与“仓库/黑板”（都要有共享数据）的区别是本节常见对比考点。

### 第3题　VIP 审核标准与折扣规则频繁变更 ✅

**题干**：某公司拟开发一个 VIP 管理系统，系统需要根据不同商场活动，不定期更新 VIP 会员的审核标准和 VIP 折扣系统。针对上述需求，采用（　）架构风格最为合适。
**选项**：A. 过程控制　B. 管道过滤器　C. 分层　D. 规则系统风格
**标准答案：D**

- **D ✅ 规则系统风格**。题干的关键词是**“不定期更新”的“标准”和“规则”**：审核标准、折扣规则属于**业务规则**，变化频繁且应由业务人员维护。规则系统把**规则**从程序逻辑中抽离出来，放入**规则库**，由**规则引擎（推理机）**做“匹配—选择—执行”循环，规则变更只改规则库、不改代码，正对需求。
- **A ❌ 过程控制**。过程控制风格面向**实时闭环控制**：传感器采集 → 控制器按设定值调节 → 执行机构动作（如化工、温度、飞行控制），强调反馈回路与实时性。VIP 管理没有受控物理过程，也没有反馈调节。
- **B ❌ 管道过滤器**。适合稳定的、线性的数据变换流程；规则本身要频繁变化，用管道意味着每次改规则都要改过滤器/改拓扑，恰恰违背需求。
- **C ❌ 分层**。分层是一种**组织原则**（表示层/业务层/数据层），解决的是“关注点分离与依赖方向”，并不解决“规则易变”的问题；规则系统内部通常也会分层实现，但本题问的是**主导风格**，应选规则系统。

**知识点**

1. 规则系统的组成：**规则库**（IF-THEN 规则集合）、**工作存储区/事实库**（当前事实）、**推理机**（匹配—冲突消解—执行）、**解释机制**。
2. 与解释器的关系：二者同属**虚拟机风格**。解释器解释执行“程序”，规则系统解释执行“规则 + 事实”，因此规则系统也叫“产生式系统”。软考/部分教材把风格分为：数据流（批处理、管道-过滤器）、调用返回（主程序-子程序、面向对象、分层）、独立构件（进程通信、事件驱动）、**虚拟机（解释器、规则系统）**、仓库（数据库、超文本、黑板）。
3. 适用判据（考场速判）：题干出现“**规则/策略/标准频繁变化**”“**业务人员可配置**”“**审核、折扣、风控、资费、计费**”→ 规则系统；“**自定义语言/脚本/指令解释执行**”→ 解释器。
4. 典型实例：专家系统（MYCIN）、Drools 规则引擎、风控规则平台、电信资费引擎。

**教材关联**：第 3 章 软件体系结构风格（风格分类）。⚠️ 本书第 3 章 §3.1 的“经典风格”六个小节未单列“规则系统”，此风格在《系统架构设计师教程》等教材中与解释器并列为**虚拟机风格**；按选项与需求特征，答案仍为 D。

### 第4题　Web 服务用什么格式描述接口与绑定 ✅

**题干**：Web 服务采用（　）格式的信息来定义和描述对外的公共接口和绑定。
**选项**：A. HTTP　B. URI　C. XML　D. SOAP
**标准答案：C**

- **C ✅ XML**。Web 服务的**接口与绑定由 WSDL 描述**，而 WSDL 是**XML 文档**：`<types>`（数据类型）、`<message>`（消息）、`<portType>`（操作集合＝接口）、`<binding>`（绑定到 SOAP/HTTP 等协议与消息格式）、`<service>`（端点地址）。题干问的是“采用什么**格式**的信息”，指向 **XML** 这一数据表示格式。
- **A ❌ HTTP**。HTTP 是**传输协议**（请求/响应、方法、状态码），负责“怎么送”，不负责“接口长什么样、绑定什么协议”。
- **B ❌ URI**。URI 是**标识/寻址**手段（`http://host:port/service`），只给出资源位置，不描述接口结构与绑定。
- **D ❌ SOAP**。SOAP 是**消息协议**（Envelope/Header/Body，基于 XML），规定“消息如何封装与传输”，它本身也需要 WSDL 来描述；把 SOAP 当作“描述接口与绑定”的格式属于概念混淆——SOAP 是**绑定的对象**，不是**描述的语言**。

**知识点**

1. Web 服务技术栈四件套：**XML**（数据表示基础）→ **SOAP**（消息协议）→ **WSDL**（服务描述：接口 + 绑定 + 端点）→ **UDDI**（注册与发现）。全部建立在 XML 之上，这正是“Web 服务”能跨平台、跨语言的根因。
2. 三组易混问法（务必分清）：
   - 问“**描述**接口与绑定”→ **WSDL（XML）**
   - 问“**通信/消息**采用什么协议”→ **SOAP**（底层可承载于 HTTP）
   - 问“**注册与发现**”→ **UDDI**
3. XML 特点：可扩展（自定义标签）、自描述、结构化、与平台/语言无关、可校验（DTD/Schema），是 SOA 的数据交换基石。

**教材关联**：第 8 章 基于服务的体系结构（Web 服务、WSDL/SOAP/UDDI）；第 6 章 可扩展标记语言（XML 语法与作用）。两章合起来就是本题的完整依据。

### 第5题　“连接件绑定的并行构件网络” ✅

**题干**：以下哪种架构风格可以概括为通过连接件绑定在一起按照一组规则运作的并行构件。
**选项**：A. 推理系统　B. C2　C. 黑板系统　D. 虚拟机
**标准答案：B**

- **B ✅ C2**。这是教材对 **C2 风格**的**原句定义**：系统由**构件**与**连接件**组成，构件之间**只能通过连接件**通信，连接件按一组规则（消息过滤、路由、广播）转发**异步消息**；构件按“层”组织（顶部/底部），可**并行**运行，且**不存在共享存储**，因此支持构件动态替换与多版本共存。
- **A ❌ 推理系统**。“推理系统/产生式系统”指规则库 + 推理机做演绎推理（专家系统），关注知识表示与推理，不涉及“连接件 + 并行构件网络”的结构描述。
- **C ❌ 黑板系统**。黑板的核心是**共享的中央数据结构**（黑板）+ 知识源 + 控制，构件通过黑板间接交互、**共享状态**；而 C2 明确**无共享状态**、消息经连接件传递，二者是最常被混淆的一对。
- **D ❌ 虚拟机**。虚拟机风格（解释器、规则系统）的特征是“解释引擎 + 被解释的程序/规则”，与“构件的连接拓扑”无关。

**知识点**

1. C2 风格五要素：**构件、连接件、消息、消息过滤、层次结构（顶部/底部）**。
2. C2 的“一组规则”：构件间不得直连；连接件是唯一通信通道；只允许**相邻层**通信；消息**异步**且可广播；构件可动态增删/替换（支持运行时演化）。
3. 与事件驱动的关系：C2 是事件驱动思想的**结构化特化**（消息通知 + 层次约束 + 连接件集中控制路由）。
4. 典型应用：GUI 密集型系统、分布式协作系统、需要运行时替换构件的系统。

**教材关联**：第 3 章 §3.1.6 C2 风格（教材原句即“通过连接件绑定在一起的按照一组规则运作的并行构件网络”）。

### 第6题　B/S 相比 C/S 的不足 ✅（教材口径）

**题干**：与 C/S 体系结构相比，B/S 体系结构也有许多不足之处，以下说法正确的是
**选项**：
A. B/S 体系结构的系统扩展能力差，但是安全性比较容易控制。
B. B/S 体系结构缺乏对动态页面的支持，没有集成有效的数据库处理能力。
C. B/S 体系结构的数据提交一般以页面为单位，数据的动态交互性不强，利于在线事务处理应用。
D. 采用 B/S 体系结构的应用系统，在数据查询等响应速度上，要远远的高于 C/S 体系结构。
**标准答案：B**（⚠️ 属“教材原文”口径，见第三部分）

- **B ✅** 与教材列出的 B/S 缺点原句一致：“**缺乏对动态页面的支持能力，没有集成有效的数据库处理功能**”。四个选项都是对教材同一段原文的**改写**，只有 B 未改动结论方向。
- **A ❌** 半对半错。教材原句是“**系统扩展能力差，安全性难以控制**”，选项中“安全性比较容易控制”被反写。补充说明：B/S 的客户端是浏览器、走公网、暴露面大（脚本注入、跨站、会话劫持），安全控制恰恰更难。
- **C ❌** 方向反了。教材原句是“数据提交一般以页面为单位，数据的动态交互性不强，**不利于**在线事务处理（OLTP）应用”。原因：整页提交/刷新、HTTP 无状态、多次网络往返、事务边界难以在客户端维持。
- **D ❌** 方向反了。教材原句是“在数据查询等响应速度上，要**远远低于** C/S 体系结构”。原因：浏览器渲染、页面重载、网络往返、服务端动态生成，均带来额外开销。

**知识点**

1. C/S（两层）：客户机承担表示逻辑 + 部分业务逻辑，服务器承担数据管理；**响应快、交互强、数据安全可控**，但**客户端需安装维护、平台相关、升级困难、扩展性受限**。
2. B/S：客户端只需浏览器，**零安装、易维护、易发布、跨平台、易扩展（服务器集群/负载均衡）**，但**交互性与响应速度弱于 C/S、安全性控制难、页面级提交不适合复杂事务**。
3. 演进路线：两层 C/S → 三层 C/S（表示层/功能层/数据层）→ B/S → RIA（Ajax/SPA）→ 微服务 + 前后端分离。这条线正好解释了“B/S 缺点”为什么在今天看起来过时。
4. ⚠️ **答题策略**：本题是“教材原文辨析题”，**按教材选 B**；不要在卷面上写“现在 B/S 也支持动态页面”——那是客观事实，但不是本题考点（详见第三部分）。

**教材关联**：第 3 章 §3.2 客户/服务器风格、§3.3 三层 C/S 结构风格、§3.4 浏览/服务器风格（B/S 优缺点原文均在此）。

### 第7题　仓库风格中“说明当前状态”的构件 ✅

**题干**：在仓库风格中，有两种不同的构件，其中，（　）说明当前状态，独立构件在中央数据存储上执行。
**选项**：A. 知识源　B. 注册表　C. 中央数据结构　D. 数据库
**标准答案：C**

- **C ✅ 中央数据结构**。教材原句：“在仓库风格中，有两种不同类型的构件：**中央数据结构说明当前状态**，**独立构件在中央数据存储上执行**。”中央数据结构（黑板/数据库/超文本）保存系统的**当前状态**，是所有独立构件共享的信息中心。
- **A ❌ 知识源**。知识源是**独立构件**（对中央数据做读写的处理单元），对应题干后半句“独立构件在中央数据存储上执行”，不是“说明当前状态”的那一个。
- **B ❌ 注册表**。注册表（registry）是仓库思想的一种**应用形态/实现**（如服务注册表、接口仓库），不是仓库风格中“说明当前状态”的**构件角色名**。
- **D ❌ 数据库**。数据库是仓库风格的**一个具体实例**（数据库系统），题干问的是**角色**（构件类型）而非实例；用“数据库”替换“中央数据结构”属于以例代名。

**知识点**

1. 仓库风格两类构件：**中央数据结构**（状态中心）+ **独立构件**（知识源/处理单元，彼此不直接通信）。
2. 按“谁触发控制”分三种子风格：
   - **数据库系统**：由**输入流**触发中央数据变更（传统 DB，事务驱动）；
   - **超文本系统**：由**用户**触发（点击跳转）；
   - **黑板系统**：由**知识源/控制构件**主动选择（启发式求解）。
3. 优点：数据集中、便于多工具协作、易加新构件、支持数据一致性管理；缺点：中央数据成为**单点瓶颈与耦合中心**，中央数据结构的设计（schema）一旦定错影响全局。
4. 典型实例：数据库 + 应用程序、IDE 的符号表/信息库、编译器的符号表、黑板系统。

**教材关联**：第 3 章 §3.1.5 仓库系统及知识库（本句为教材原句，属必背定义）。

### 第8题　软件体系结构描述方法 ⚠️

**题干**：以下关于软件体系结构描述方法说法错误的是
**选项**：
A. 图形化工具在软件设计中占据主导地位。
B. 基于构件的系统描述语言将软件系统描述成一种以特定形式相互作用的特殊软件实体构造组成的组织或系统。
C. 由于软件设计语言和模块内连接语言具有严格的语义基础，因此能支持描述较小的软件单元。
D. 软件体系结构描述语言是参照传统程序设计语言的设计和开发经验，重新设计、开发和使用的针对软件体系结构的描述语言。
**标准答案：C**

- **C ❌（即本题要选的“错误说法”）**。这句话的**因果链**不成立：软件设计语言（PDL）与模块内连接语言（MIL）**缺乏严格的语义基础**，因此它们**只能描述较小的软件单元**（模块接口与连接关系），无法支撑大规模系统的精确描述与自动分析。选项把“缺乏严格语义”偷换成“具有严格的语义基础”，用错误的理由支撑一个看似合理的结论，故为错误项。
- **A ✅（正确说法）**。教材原句：“图形化工具在软件体系结构描述中占据主导地位。”它直观、便于与涉众交流，是工程实践中最常用的描述手段（框图、UML 图）。
- **B ✅（正确说法）**。这正是“基于构件的系统描述语言”的定义：把系统描述成**由特殊软件实体（构件）以特定形式相互作用**构成的组织/系统，强调构件与连接关系。
- **D ✅（正确说法）**。ADL 是**参照传统程序设计语言的设计与开发经验**重新设计、开发、使用的**体系结构级**描述语言，具备形式化语义，可支持一致性检查、演化与代码生成（代表：Wright、C2-SADL、Rapide、UniCon、Darwin、Acme、AADL）。

**知识点**

教材归纳的体系结构描述方法有四类，对比表如下：

| 方法 | 强项 | 短板 |
|---|---|---|
| 图形化工具 | 直观、易交流、占主导 | 语义不精确、不可自动分析、规模受限 |
| 基于构件的描述语言 | 明确构件/连接件/配置 | 表达力与工具支持有限 |
| 软件设计语言 PDL / 模块内连接语言 MIL | 贴近实现、可描述接口与连接 | **缺乏严格语义基础，只适合较小单元** |
| ADL（体系结构描述语言） | 形式化语义、可分析/可演化/可生成 | 学习成本高、工具生态弱 |

1. ADL 的构成要素：**构件、连接件、配置（体系结构）、约束/风格**；四种基本描述能力：结构、行为、交互、约束。
2. ⚠️ 判卷口径：本题答案键为 C。若你手上课件的原句是“……因此能支持描述**较大**的软件单元”，该句同样错误（结论也反了），答案仍是 C；若课件把该句写成“缺乏严格语义基础，只能描述较小的软件单元”并判“对”，则说明课件与题库版本不同——此时应以课件为准，但这种版本差异极少见。

**教材关联**：第 4 章 软件体系结构描述（四种方法的对比是本章核心表格，建议整表背诵）。

### 第9题　MVC 三要素（填空）

**题干**：MVC 模式的中的 M，V，C 分别对应＿＿＿＿＿、View、＿＿＿＿＿。
**标准答案**：第 1 空 **Model（模型）**；第 2 空 **Controller（控制器）**

- **M = Model（模型）**：封装**业务数据与业务逻辑**，提供数据访问与状态变更接口，不关心如何显示。
- **V = View（视图）**：负责**数据显示与呈现**，从模型读取数据渲染界面，可有多个视图对应同一模型。
- **C = Controller（控制器）**：接收**用户输入**，解析并调用模型完成业务处理，再**选择/更新视图**，是模型与视图之间的协调者。
- 三者的关系：**视图与模型解耦**（观察者模式：模型变更通知视图刷新），控制器集中处理交互逻辑 → 关注点分离、可复用、可测试。

**知识点**

1. MVC 最早出现于 **Smalltalk-80** 的图形界面框架，后在 Java（Struts/Spring MVC）、.NET、前端框架（Angular/React/Vue 的 MVVM）中广泛使用；教材在**富互联网应用（RIA）** 一章中以 MVC 作为 RIA 的体系结构基础。
2. 变体辨析：**MVC**（控制器协调，视图可直达模型）→ **MVP**（Presenter 完全隔断视图与模型，便于单元测试）→ **MVVM**（ViewModel 双向绑定，前端主流）。
3. 优点：职责分离、模型可复用、视图可替换、便于分工与测试；缺点：控制器易膨胀、简单界面反而增加复杂度、视图与模型的同步成本。
4. 填空写法提示：中英文任一即可，建议写“Model（模型）”“Controller（控制器）”，避免只写中文单字。

**教材关联**：第 9 章 富互联网应用体系结构（MVC 模式）；也可与第 5 章 UML 的“包图/构件图”配合理解分层与依赖。

### 第10题　黑板系统的组成（填空）

**题干**：黑板系统主要由＿＿＿＿＿、＿＿＿＿＿和控制组成。
**标准答案**：第 1 空 **知识源**；第 2 空 **黑板**（可写“黑板结构”“中央数据结构”“共享数据”）

- **知识源（Knowledge Source, KS）**：领域专家知识的封装，各自独立、只与黑板交互，**彼此不直接通信**；当自身激活条件满足时向黑板写入/修改假设。
- **黑板（Blackboard）**：**共享的中央数据结构**，保存问题求解的当前状态（原始数据、部分解、假设、置信度），是知识源之间唯一的间接通信媒介。
- **控制（Control）**：**调度机制**，根据黑板状态决定“下一步激活哪个知识源”，并负责冲突消解、终止判断，避免知识源无序触发。

**知识点**

1. 黑板系统的本质 = **仓库风格 + 启发式控制**：数据驱动 +  opportunistic（机会主义）求解，适合**问题无确定算法、需多知识源协作**的场景。
2. 经典实例：**HEARSAY-II 语音识别**（教材标准案例，其黑板按层次组织为参数级/音节级/词级/句级）、图像理解、信号处理、专家系统、协同设计。
3. 优缺点：优点——知识源可独立开发/替换、支持异构知识表示、适合增量式求解；缺点——**控制策略难设计**（调度与终止）、黑板结构（schema）设计困难、性能与调试成本高、难以保证解的质量。
4. 与“事件驱动”的区别：黑板是**共享数据 + 集中调度**（拉模式/状态驱动），事件驱动是**消息广播 + 订阅**（推模式/事件驱动）——第 2、5 题都围绕这条界线出题。

**教材关联**：第 3 章 §3.1.5 仓库系统及知识库（黑板系统三要素为教材原文，属必背）。

### 第11题　Web 服务的三种逻辑构件（填空）

**题干**：一个完整的 Web 服务包括 3 种逻辑构件：服务提供者、＿＿＿＿＿、＿＿＿＿＿。
**标准答案**：第 1 空 **服务请求者**（服务使用者/服务消费者）；第 2 空 **服务注册中心**（服务代理/注册中心/UDDI 注册中心）

- **服务提供者（Service Provider）**：拥有并实现服务，**发布**服务描述（WSDL）到注册中心，并响应调用。
- **服务请求者（Service Requester / Consumer）**：需要服务的应用，向注册中心**查找**服务描述，据绑定信息**调用**服务。
- **服务注册中心（Service Registry / Broker）**：服务描述的**发布与检索**场所（UDDI），充当“黄页”，使请求者无需预先知道提供者位置。

**知识点**

1. 三种角色对应三种基本操作：**发布（Publish）— 查找（Find）— 绑定/调用（Bind）**；教材常画成“三角关系图”，是 SOA 一章的必考图。
2. 三个技术支撑：**WSDL**（描述，XML）、**SOAP**（消息，XML）、**UDDI**（注册发现），即第 4 题的延伸。
3. 术语差异 ⚠️：有的教材写“服务代理（Service Broker）”，有的写“服务注册中心”；有的写“服务使用者/服务消费者”而非“服务请求者”。三种写法都算对，建议答题时写“服务请求者（服务使用者）”“服务注册中心（服务代理）”。
4. Web 服务的优点：**松耦合、平台/语言无关、可组合（编排）**；缺点：XML 冗长导致性能开销、SOAP 复杂度高、治理与安全（WS-Security）复杂 → 这也是后来 REST/微服务兴起的原因。

**教材关联**：第 8 章 基于服务的体系结构（Web 服务三构件、三操作、三协议）。

### 第12题　C/S 体系的三个组成部分（填空）

**题干**：C/S 体系结构有三个主要组成部分：＿＿＿＿＿、网络、＿＿＿＿＿。
**标准答案**：第 1 空 **客户机**（客户端）；第 2 空 **服务器**

- **客户机（Client）**：前端，承担**表示逻辑**（界面、输入校验）和部分业务逻辑，向服务器发起请求。
- **服务器（Server）**：后端，承担**数据管理与核心业务逻辑**（数据库服务器/应用服务器），响应请求并保证数据一致性与并发控制。
- **网络（Network）**：连接客户机与服务器的通信设施（局域网/广域网、协议栈、中间件），决定系统的分布范围与性能。

**知识点**

1. 两层 C/S：客户机（胖客户端）+ 服务器（数据库）；**三层 C/S**：**表示层（客户机）— 功能层（应用服务器）— 数据层（数据库服务器）**，把业务逻辑从客户端上移，解决“胖客户端维护难”的问题。
2. C/S 的优点：交互性强、响应速度快、界面丰富、数据处理能力强、安全性较易在局域网内控制。
3. C/S 的缺点：**客户端需逐一安装与升级**（部署成本高）、**平台/环境相关**（可移植性差）、**扩展性受限**（连接数与并发瓶颈）、异地/多用户场景维护困难 → 由此演化出 B/S。
4. 记忆口诀：**“客户机—网络—服务器”三点一线**；三层则再加“功能层”把业务逻辑独立出来。

**教材关联**：第 3 章 §3.2 客户/服务器风格、§3.3 三层 C/S 结构风格（教材明确给出 C/S 三要素与三层划分）。

### 第13题　构件可以由其他构件连接而成（判断）

**题干**：构件可以由其他复合构件和原子构件通过连接而成。
**标准答案：A 对**

- **理由**：构件按粒度分为**原子构件（primitive/原子）**与**复合构件（composite）**。原子构件是最小可复用单元、不可再分；复合构件由若干原子构件和/或复合构件**通过连接件（connector）装配而成**，并对外暴露**端口（port）**。因此“由其他复合构件和原子构件通过连接而成”正是**复合构件的定义**。
- **易错点**：不要与“构件必须独立部署/必须是二进制可执行单元”混淆——教材的构件是**逻辑上的可复用软件单元**，粒度可大可小。
- **延伸**：体系结构核心模型的五要素是**构件、连接件、配置、端口、角色**，其中构件 + 连接件 + 配置是**最基本**的三元素（这是同源高频考点）。

**教材关联**：第 1 章 §1.2 构件与软件重用（构件模型、构件获取/管理/重用）；第 2 章 §2.4 抽象模型（构件、连接件、端口、角色）。

### 第14题　基于事件的隐式调用（判断）

**题干**：基于事件的隐式调用风格的思想是构件不直接调用一个过程，而是触发或广播一个或多个事件。
**标准答案：A 对**

- **理由**：这是教材对隐式调用（事件驱动）的**定义原句**。构件不持有其他构件的引用、不做显式过程调用，而是**发布事件**；订阅了该事件的构件被**隐式调用**（由事件机制负责分发）。调用关系被“事件”这一间接层解耦，因此称为“隐式”调用。
- **易错点**：隐式 ≠ 异步的必然；隐式调用的本质是**控制流反转与解耦**，同步/异步是实现细节。另注意它对“**谁被调用、何时被调用**”不作保证。
- **延伸**：与“显式调用”（主程序-子程序、面向对象的方法调用）对比：显式调用编译期即确定调用目标，隐式调用运行期由事件匹配决定。

**教材关联**：第 3 章 §3.1.3 基于事件的系统（教材原句，判断题高频）。

### 第15题　分层系统“不支持重用”（判断）

**题干**：层次系统中支持抽象程度递增的系统设计是设计师可以把一个复杂系统按照递增的步骤进行分解，同时支持功能增强，但是不支持重用。
**标准答案：B 错**

- **理由**：教材给出的分层系统**三大优点**正是：**① 支持抽象程度递增的系统设计**（自底向上逐层抽象）；**② 支持功能增强**（每层可独立扩展）；**③ 支持重用**（同一层/同一接口可被多处复用，标准化的层接口使上层可在不同实现上复用）。题干把第三点说成“不支持重用”，与原文相反。
- **易错点**：分层系统的**缺点**才是“并非所有系统都能分层、层次划分与接口设计困难、跨层调用带来性能损失、层次过多导致效率下降”——出题人常把“缺点”与“优点”互换来制造错误项。
- **延伸**：分层与“客户机/服务器”“三层 C/S”的关系：三层 C/S 就是分层的特例（表示层/功能层/数据层）；分层也是“抽象层次递增”的典型体现（OSI 七层、TCP/IP 四层、操作系统内核分层）。

**教材关联**：第 3 章 §3.1.4 分层系统（优点/缺点列表为必背内容）。

### 第16题　体系结构是理解构件及其关系的框架（判断）

**题干**：软件体系结构充当一个理解系统构件和它们之间关系的框架，特别是那些始终跨越时间和实现的属性。
**标准答案：A 对**

- **理由**：这是教材引用的体系结构**定义之一**（源自 SEI/Bass、Clements、Kazman 的表述）：体系结构是**理解系统构件及其相互关系**的框架，尤其关注那些**跨越时间与实现而持久存在**的属性（即不随某次实现、某项技术选型而改变的**结构与质量属性**）。这也解释了为什么体系结构能作为涉众沟通、复用与演化的基础。
- **易错点**：“跨越时间和实现的属性”不是“运行期属性”，而是指**稳定的、本质的结构性属性**；不要理解成“性能/可用性”这类运行期质量属性。
- **延伸**：三个常见定义可对照记忆——
  1. **IEEE 1471 / ISO 42010**：体系结构是体现在**构件、构件间关系和环境**中的基本概念或属性。
  2. **Perry & Wolf**：`SA = {Elements, Form, Rationale}`（元素、形式、原理）。
  3. **教材/SEI**：构件 + 关系 + 约束/原则，是理解系统的框架，关注持久属性。

**教材关联**：第 1 章 §1.3.1 软件体系结构的定义（教材罗列多家定义并作比较，本题取自其中一条）。

### 第17题　开发视图支持功能需求（判断）

**题干**：开发视图主要支持系统的功能需求，即系统提供给最终用户的服务。
**标准答案：B 错**

- **理由**：支持**功能需求**（系统向最终用户提供的服务）的是**逻辑视图（Logical View）**；**开发视图（Development View，又称模块视图/实现视图）** 关注的是**软件模块的组织与管理**：包/子系统/层的划分、源文件与构建单元、复用与依赖、开发分工与配置管理，面向**程序员/开发管理者**。
- **易错点**：4+1 视图的“功能需求归属”是高频陷阱题。请记牢：**逻辑视图管功能，开发视图管模块组织，进程视图管并发与性能，物理视图管部署，场景把四者串起来做验证**。
**延伸**：4+1 视图（Kruchten, 1995）速记表如下，务必整表记住“谁管什么”。

| 视图 | 关注点 | 面向人员 | 静态/动态 | 主要质量属性 |
|---|---|---|---|---|
| 逻辑视图 | 功能需求、对象模型、类与关系 | 最终用户、分析设计人员 | 静态为主 | 功能、可理解性 |
| 开发视图 | 模块/包/层组织、构建与复用 | 程序员、开发管理者 | 静态 | 可维护性、可复用性、可移植性 |
| 进程视图 | 进程/线程、并发、同步、通信 | 系统集成人员 | 动态 | 性能、吞吐、并发 |
| 物理视图 | 软件到硬件的映射、部署与分布 | 系统工程师、运维 | 静态（拓扑） | 可用性、可伸缩性、可靠性 |
| 场景（+1） | 用例驱动，验证上述视图 | 全部涉众 | 动态 | 一致性、可验证性 |

**教材关联**：第 2 章 §2.1 “4+1”视图模型（§2.1.1 逻辑视图、§2.1.2 开发视图为本题直接依据）。

### 第18题　体系结构是可运行的软件产品（判断）

**题干**：软件体系结构不只是一种对软件系统的表示和描述，也是一种可运行的软件产品。
**标准答案：B 错**

- **理由**：体系结构是**抽象的设计蓝图/结构描述**，回答“系统由哪些构件、如何连接、遵循什么约束”，它**本身不可执行**；可运行的产物是**构件、框架、程序**。把体系结构等同于“可运行的产品”混淆了**设计层**与**实现层**。
- **易错点**：体系结构虽不可运行，但可以通过**框架/中间件/产品线**“实例化”为可运行骨架（如 MVC 思想落地为 Spring MVC），这正是 §12“基于体系结构的软件开发”讨论的内容——但**实例化 ≠ 体系结构本身可运行**。
- **延伸**：四个概念的关系（考点密集），见下表。

| 概念 | 是否可运行 | 说明 |
|---|---|---|
| 软件体系结构 | 否 | 构件 + 连接件 + 配置 + 约束的抽象结构 |
| 框架 | 是（半成品） | 体系结构的**部分实现**，含可复用骨架与扩展点，需填充业务代码 |
| 设计模式 | 否 | 面向特定问题的**可复用设计经验**（类/对象级） |
| 构件 | 是 | 可独立部署/复用的软件单元 |

**教材关联**：第 1 章 §1.3.1 定义（体系结构是抽象描述而非实现）；第 12 章 基于体系结构的软件开发（体系结构到实现的映射与框架）。

## 四、考点归纳（第 1–4、8 章脉络）

### 4.1 八种架构风格总表（本套题的主战场）

| 风格 | 构件 | 连接件 | 数据/控制 | 优点 | 缺点 | 典型应用 |
|---|---|---|---|---|---|---|
| 管道-过滤器 | 过滤器（独立处理步骤） | 管道（单向数据流） | 数据流式传递，过滤器间不共享状态 | 可理解/可重用/可替换、支持并发、易扩展 | 不适合交互式、格式协商开销、批处理延迟、错误处理难 | Unix 管道、**编译器**、图像/信号处理、ETL |
| 数据抽象/面向对象 | 对象（封装数据与操作） | 方法调用/消息 | 数据与操作封装在对象内 | 易理解、封装性好、可复用 | 对象需知道彼此身份、调用链耦合 | 大多数 OO 系统、GUI 框架 |
| 事件驱动（隐式调用） | 事件发布者/订阅者 | 事件总线/分发器 | 事件广播，构件不直接调用 | 松耦合、易演化、支持异步 | 控制流难推理、不保证顺序、调试难 | **新闻推送**、GUI、消息中间件、微服务事件 |
| 分层 | 层内构件 | 层间接口（单向依赖） | 每层为上层提供服务，跨层受限 | 抽象递增、功能增强、**支持重用** | 非万能分层、接口设计难、性能损失 | OSI/TCP-IP、三层 C/S、协议栈 |
| 仓库/黑板 | 中央数据结构 + 知识源 | 共享数据访问 | 中央数据存当前状态，知识源围绕其执行 | 数据集中、多工具协作、易加构件 | 中央数据瓶颈、schema 难设计、控制复杂 | 数据库、IDE 信息库、**HEARSAY-II** |
| C2 | 构件（分层组织） | 连接件（消息路由/过滤） | 异步消息、**无共享存储** | 支持并行、动态替换、松耦合 | 消息开销、规则约束多 | GUI 密集系统、分布式协作 |
| 解释器 | 解释引擎 + 被解释程序 | 内部状态访问 | 逐句解释执行 | 灵活支持新语言/脚本 | 性能低、实现复杂 | 脚本引擎、虚拟机、SQL 解释器 |
| 规则系统 | 规则库 + 推理机 | 事实/规则匹配 | 匹配—选择—执行循环 | **规则易变、业务可维护** | 规则冲突、推理效率、验证难 | 专家系统、**VIP 审核与折扣**、风控、计费 |

### 4.2 客户/服务器家族对比（第 6、12 题）

| 维度 | 两层 C/S | 三层 C/S | B/S |
|---|---|---|---|
| 组成 | 客户机 + 网络 + 服务器 | 表示层 + 功能层 + 数据层 | 浏览器 + Web 服务器/应用服务器 + 数据库 |
| 业务逻辑位置 | 客户端（胖） | 功能层（应用服务器） | 服务端 |
| 部署维护 | 客户端逐台安装升级 | 中间层集中维护 | 零安装，服务端升级 |
| 交互/响应 | 强 / 快 | 较强 / 中 | 弱 / 慢（教材口径） |
| 安全性 | 局域网内较易控制 | 较易控制 | 难控制（公网、浏览器） |
| 扩展性 | 受连接数限制 | 较好 | 最好（集群/负载均衡） |
| 典型场景 | 企业内部 MIS | 大型企业应用 | 信息发布、电商、SaaS |

### 4.3 Web 服务体系结构（第 4、11 题）

| 角色 | 操作 | 支撑技术 |
|---|---|---|
| 服务提供者 | **发布**服务描述（Publish） | WSDL 文档（XML） |
| 服务注册中心（服务代理） | 存储/检索服务描述 | **UDDI** |
| 服务请求者（服务使用者） | **查找**（Find）→ **绑定调用**（Bind） | SOAP 消息（XML）+ HTTP 传输 |

### 4.4 三个“必背原句”（教材原话，判断题/填空题直接命中）

1. 仓库风格：“中央数据结构说明当前状态，独立构件在中央数据存储上执行。”
2. 黑板系统：“由知识源、黑板和控制三部分组成。”
3. 隐式调用：“构件不直接调用一个过程，而是触发或广播一个或多个事件。”

## 五、答题与复盘建议

1. **单选题的“最合适”原则**：这 8 题有 5 题（1、2、3、5、6）是“四选一最优”，判据是**题干关键词 → 风格特征**的映射：线性逐级变换→管道；订阅/推送/广播→事件驱动；规则频繁变更→规则系统；连接件绑定的并行构件网络→C2；共享中央数据→仓库/黑板。**先抓关键词，再排除同名近亲（管道 vs 仓库、事件 vs 黑板、C2 vs 黑板）**。
2. **填空题按“关键词给分”**：中英文双写最稳（Model（模型））；第 10、11 题的第 2 空允许同义替换，写成“黑板（中央数据结构）”“服务注册中心（服务代理）”不会扣分。
3. **判断题要写理由**（若老师要求）：一律套“**教材原句 + 反向修正**”句式，如第 15 题：“分层系统三大优点为抽象递增、功能增强、**支持重用**，题干‘不支持重用’与原文相反，故错。”
4. **易错清单（考前 10 分钟看）**：① 开发视图 ≠ 功能需求（逻辑视图才是）；② 体系结构不可运行；③ 分层**支持**重用；④ 黑板 = 知识源 + 黑板 + 控制；⑤ WSDL（描述）≠ SOAP（消息）≠ UDDI（注册）；⑥ C2 无共享存储、黑板有共享数据；⑦ B/S 缺点按教材四句原文背（动态页面/数据库处理、响应慢、页面级提交不利 OLTP、扩展差安全性难控）。
5. **变体预警**：把“编译器”换成“多个工具围绕共享数据”→ 仓库；把“推送”换成“多知识源协作求解”→ 黑板；把“规则变更”换成“自定义脚本解释执行”→ 解释器；把“C2”换成“消息总线/发布订阅”→ 事件驱动（层次消息总线是 C2 的近亲）。**这四个替换是期末卷最可能出现的“同题变形”。**
