### 第1题 用例模型的主要作用

**题目**：用例模型的主要作用是什么（　）
A、定义系统的内部算法和数据结构。
B、与用户沟通的功能需求工具，划定系统边界，明确系统功能范围。
C、指定系统的网络配置和硬件需求。
D、替代项目的开发计划和时间表。

**参考答案：B** ✅

**解析**：用例模型从参与者（用户、外部系统）的视角描述系统"做什么"，用一组用例和参与者表示系统与外界的一次次完整交互，因而是需求获取与需求确认阶段**与用户沟通的主要工具**；同时用例图天然给出了**系统边界**（哪些职责在系统内、哪些由外部参与者承担），从而明确功能范围。
- A 错：内部算法与数据结构属于软件设计与实现的内容，是"怎么做"，不是用户视角的功能需求。
- C 错：网络配置、硬件需求属于部署需求/非功能需求（物理环境约束），用例模型不描述它们。
- D 错：用例模型不承担进度计划职能，项目计划由项目管理过程产生（教材第 6 章）。

**教材对应**：第4章 §4.2 需求开发（需求建模、用例模型）。

### 第2题 需求跟踪矩阵的主要目的

**题目**：需求跟踪矩阵的主要目的是什么（　）
A、估算项目开发成本。
B、跟踪每个需求的状态（如未开始、进行中、已完成）。
C、建立从需求起源到设计和测试的链接，确保覆盖并分析变更影响。
D、用于向客户展示最终产品功能。

**参考答案：C** ✅

**解析**：需求跟踪矩阵（RTM）建立需求与其来源（业务需求、用户需求、合同条款）、后续工作产品（设计元素、代码、测试用例）之间的**双向链接**，用途有两个：一是**验证覆盖**（每个需求都有对应的设计与测试，也没有多余的设计元素）；二是**变更影响分析**（某需求变更时，顺着链接找出所有受影响的设计、代码、测试与文档）。
- B 是"需求状态跟踪"，属于需求管理活动之一，可由需求管理工具完成，但它只是 RTM 的附带用途，不是主要目的；RTM 的核心是"可追溯性"。
- A、D 分别属于估算与演示，与跟踪矩阵的核心作用无关。

**教材对应**：第4章 §4.3 需求管理（需求跟踪）、§4.1 需求管理的模型和流程。

### 第3题 业务需求与用户需求

**题目**：关于"业务需求"和"用户需求"，以下说法正确的是（　）
A、业务需求是宏观的、组织层面的目标，而用户需求是具体的、用户需要完成的任务。
B、业务需求是技术团队制定的，用户需求是市场部门制定的。
C、业务需求和用户需求是同一概念的不同说法。
D、用户需求比业务需求更重要。

**参考答案：A** ✅

**解析**：需求的三个层次自上而下为业务需求、用户需求、系统需求。业务需求描述组织/客户希望达成的业务目标（提高市场占有率、降低成本、满足合规要求等），是**宏观的、组织层面的**；用户需求描述用户为完成任务必须让系统提供什么，通常用用例、场景、用户故事表达，是**具体的、使用视角的**。
- B 错：与"谁制定"无关，两类需求都可能由客户、市场人员、需求分析人员共同获得。
- C 错：二者层次不同，不能混为一谈。
- D 错：三个层次是派生与追溯关系，不存在简单的重要性排序；业务需求是源头，用户需求是其在用户任务层面的体现。

**教材对应**：第4章 §4.2 需求开发（需求层次/需求类型）。

### 第4题 需求验证的主要目的

**题目**：在需求工程中，"需求验证"的主要目的是什么（　）
A、确保需求文档没有语法和拼写错误。
B、确保所描述的需求准确完整地反映用户的真实意图，并且是可行的。
C、确保需求能够通过最新的技术来实现。
D、确保需求得到项目管理者的批准。

**参考答案：B** ✅

**解析**：需求验证（requirements verification）是在需求文档形成后对其质量进行检查，确认需求**正确、完整、一致、无二义、可验证、必要、可行**，即确保需求文档真实反映了用户意图，而不是分析人员的臆测。
- A 只是文档质量检查的一小部分（拼写检查甚至算不上"验证"）。
- C 只强调技术可行性，遗漏正确性、完整性、一致性等更核心的内容；且"最新技术"不是可行性判据，成本、进度、现有技术条件都要考虑。
- D 属于评审与批准流程的形式动作，不是验证的目的。

**术语提示**：中文教材中"需求验证"常指"检验需求规格说明写对了没有"，与"需求确认（validation，确认做出来的产品满足需求）"分处不同阶段，不要与第 7 题混淆。

**教材对应**：第4章 §4.2 需求开发（需求验证）、§4.3 需求管理。

### 第5题 软件过程的实施与持续改进

**题目**：建立软件过程后，为确保其有效实施和持续改进，应采取什么措施（　）
A、强制开发团队遵循过程，不进行任何调整
B、定期对过程进行审查、评估和改进
C、仅在项目出现问题时才考虑调整过程
D、依赖开发团队的自发性和创新性来优化过程

**参考答案：B** ✅

**解析**：过程建立只是起点，过程管理是 PDCA 式闭环：定义过程 → 执行过程 → 度量与审查 → 评估与改进。因此应**定期开展过程审查与过程评估**（依据 CMM/CMMI、ISO 15504 等），并依据度量数据与项目反馈裁剪、优化过程。
- A 错：完全僵化会脱离项目实际，过程必须允许裁剪。
- C 错："出了问题才改"是被动救火，缺乏预防与持续改进。
- D 错：改进应有组织、有数据、有制度支撑，不能只靠个人自发。

**教材对应**：第1章 §1.2 过程规范；第9章 §9.1 过程模型的剪裁、§9.4 过程评估、§9.5 过程改进的模型和方法。

### 第6题 强调顺序性的过程模型

**题目**：以下哪个模型强调顺序性，每个阶段完成后才能进入下一个阶段（　）
A、敏捷模型　B、瀑布模型　C、螺旋模型　D、V 模型

**参考答案：B** ⚠️

**解析**：瀑布模型把软件生存周期严格划分为需求分析、设计、编码、测试、维护等阶段，阶段之间具有**顺序性和依赖性**：前一段的文档是后一段的输入，必须完成上一阶段并评审通过才能进入下一阶段。
- A 错：敏捷以短迭代、快速反馈为特征，不是严格顺序推进。
- C 错：螺旋模型是迭代的，每轮都有风险分析与评审，也不是"完成一个阶段才进入下一个"。
- D 干扰项：V 模型也是串行模型，但它的标志性特征是**开发活动与测试活动一一对应、强调测试的重要性**；题干"每个阶段完成后才能进入下一个阶段"是对**瀑布模型**最经典的表述，因此选 B。

**易错点**：V 模型与瀑布模型同属串行，但"顺序性/阶段依赖"的教科书定义句属于瀑布模型。

**教材对应**：第1章 §1.5.1 软件过程模型。

### 第7题 需求确认的必要性

**题目**：下列哪种情况最能体现"需求确认"的必要性（　）
A、开发团队发现两个需求在技术实现上存在依赖关系。
B、项目经理需要向管理层汇报项目进度。
C、测试团队需要知道哪些测试用例覆盖了某个特定功能。
D、客户在验收产品时，发现实现的功能与自己的预期不符。

**参考答案：D** ✅

**解析**：需求确认（validation）回答"我们是否在做正确的事"，即确认产品/需求描述与用户真实预期一致。D 正是**确认失败的直接表现**：事先没有与用户一起确认需求，交付物与预期不符，导致验收不通过、返工甚至纠纷，最能说明需求确认的必要性。
- A 属于需求一致性/依赖分析（验证范围）。
- B 属于项目沟通与进度报告。
- C 属于需求跟踪（覆盖关系）。

**教材对应**：第4章 §4.2 需求开发（需求确认/需求评审）、§4.3 需求管理。

### 第8题 需求变更控制流程的核心目标

**题目**：一个有效的需求变更控制流程，其核心目标是（　）
A、杜绝所有需求变更，以保护项目计划。
B、确保所有变更都经过快速、非正式的评估和批准。
C、确保变更被有效管理，评估其影响并得到批准，同时保持需求文档的完整性。
D、将变更决策权完全交给开发团队。

**参考答案：C** ✅

**解析**：需求变更不可避免，变更控制的目的不是"禁止变更"，而是让变更**有序、可控、可追溯**：提出变更申请 → 影响分析 → 变更控制委员会（CCB）评审批准 → 实施 → 验证 → 基线更新与通知。C 完整覆盖"管理、影响评估、批准、文档完整性"四个要点。
- A 错：禁止变更既不现实，也会造成需求与产品脱节。
- B 错："快速、非正式"恰恰是失控表现，重大变更必须正式评估与批准。
- D 错：决策权属于 CCB（客户、项目经理、开发与测试代表等组成），不能单交给开发团队。

**教材对应**：第4章 §4.3 需求管理；附录A §A.4 需求变更管理过程规范。

### 第9题 需求评审中发现需求冲突

**题目**：在需求评审会议上，发现两个需求之间存在逻辑冲突。这属于需求管理中哪个环节需要解决的问题（　）
A、需求获取　B、需求验证　C、需求变更控制　D、需求优先级排序

**参考答案：B** ⚠️

**解析**：需求评审是需求验证的典型手段，评审检查内容包括正确性、完整性、一致性、无二义性、可验证性等；"两个需求之间存在逻辑冲突"属于**一致性检查**发现的问题，因此在需求验证环节解决。
- A 需求获取是收集需求的阶段，它可能埋下冲突的种子，但"通过评审发现冲突"属于验证。
- C 变更控制处理的是需求基线的变更，不是需求之间的静态冲突。
- D 优先级排序解决"先做谁"，不解决逻辑矛盾。

**术语提示**：若课件把"需求分析/需求验证"合并为"需求分析"阶段，也可表述为"在需求分析（验证）过程中解决"，但按题干的"评审会议"情境，标准答案为需求验证。

**教材对应**：第4章 §4.2 需求开发（需求验证/需求评审）。

### 第10题 合适的用例

**题目**：以下哪一项最适合作为"图书管理系统"中的一个用例（　）
A、数据库连接　B、显示主界面　C、查询图书　D、图书类（Book Class）

**参考答案：C** ✅

**解析**：用例是参与者（读者、图书管理员）使用系统完成的一项**对参与者有价值**的完整功能。"查询图书"由读者发起、系统响应并返回结果，具有明确的业务价值，是标准用例。
- A 是内部技术实现细节，不是参与者可见的目标。
- B "显示主界面"是实现细节/界面行为，粒度与价值都不适合作为用例（可归入界面设计）。
- D 是设计阶段的类，属于结构元素，不是功能需求。

**教材对应**：第4章 §4.2 需求开发（用例建模）。

### 第11题 CMM 中关键过程域（KPA）的定义

**题目**：以下哪项是 CMM 中"关键过程域（KPA）"的核心定义（　）
A、组织为达到特定成熟度等级必须实施的活动
B、量化监控过程性能的统计工具
C、项目计划中定义的里程碑
D、自动化测试工具的使用规范

**参考答案：A** ✅

**解析**：KPA（Key Process Area）是 CMM 中一组相关联的活动，当这些活动全部实施时，就能达到一组对达成该成熟度等级至关重要的目标。换言之，KPA 是"组织为达到某一成熟度等级**必须实施的活动**集合"，每个 KPA 由若干**目标（Goals）** 与**关键实践（Key Practices）** 构成。
- B 属于"量化过程管理/统计过程控制"的做法（成熟度 4 级内容），不是 KPA 的定义。
- C 属于项目计划范畴；D 属于工具与测试技术，与 KPA 定义无关。

**教材对应**：第2章 §2.2 能力成熟度模型概述、§2.3 过程成熟度级别（§2.3.3 成熟度等级的过程特征、§2.3.4 CMMI 过程域）。

### 第12题 Level 4（量化管理级）的典型过程域

**题目**：在 CMM/CMMI 模型中，哪个过程域属于 Level 4（量化管理级）的典型要求（　）
A、需求开发　B、技术解决方案　C、量化项目管理　D、风险管理和集成

**参考答案：C** ✅

**解析**：CMMI 中 4 级（已量化管理级）的两个标志性过程域是**组织过程性能（OPP）** 与**量化项目管理（QPM）**，其核心是用统计与量化方法管理过程性能与项目，使过程可预测。
- A 需求开发（RD）、B 技术解决方案（TS）属于 3 级（已定义级）的过程域。
- D 风险管理（RSKM）、产品集成（PI）也都是 3 级过程域，均非 4 级特征。

**教材对应**：第2章 §2.3 过程成熟度级别（§2.3.4 CMMI 过程域、§2.3.5 CMM 和 CMMI 过程域的比较分析）。

### 第13题 ISO 12207 标准的主要作用

**题目**：ISO 12207 标准的主要作用是什么（　）
A、提高软件开发的效率
B、确保软件过程的一致性、可重复性和高质量
C、降低软件开发的成本
D、促进软件产品的国际化

**参考答案：B** ⚠️

**解析**：ISO/IEC 12207《软件生存周期过程》为软件的获取、供应、开发、运行、维护等建立共同的过程框架，明确每一过程的活动与任务，使不同组织、不同项目可以采用共同语言和一致的做事方式，从而保证过程的**一致性、可重复性**，并以此支撑产品质量。
- A、C 是规范过程可能的**收益/结果**，不是标准的主要作用（效率与成本取决于组织的执行能力，标准本身不保证）。
- D 与标准内容无关。

**口径提示**：本教材第1章把生存周期的过程需求划分为**软件工程过程、软件支持过程、软件管理过程、软件组织过程、客户—供应商过程**五类；而经典 ISO/IEC 12207:1995 采用**基本过程、支持过程、组织过程**三类划分（共 17 个过程）。答题按题目所问口径作答，两者不矛盾（详见简答题第 3 题）。

**教材对应**：第1章 §1.3 软件生命周期的过程需求、§1.4 软件生命周期标准（§1.4.1 ISO/IEC 标准体系）。

### 第14题 建立软件过程应考虑的因素

**题目**：为了建立有效的软件过程，应该参考哪些因素（　）
A、仅考虑开发团队的经验
B、忽略项目的规模和复杂度
C、综合考虑项目特点、团队能力、行业标准和最佳实践
D、仅仅遵循最新的敏捷开发方法

**参考答案：C** ✅

**解析**：过程定义必须"量体裁衣"：既符合组织的业务目标与项目特点（规模、复杂度、需求稳定度、交付压力、行业监管要求），又匹配团队能力与成熟度，还要参考行业标准（ISO/IEC 12207、IEEE 标准体系）与最佳实践（CMM/CMMI、PSP/TSP、敏捷等），最后通过**裁剪**形成适合本项目的过程。
- A、D 以偏概全（只看经验，或把某一种方法当唯一标准）；B 忽略规模与复杂度会导致过程过重或过轻。

**教材对应**：第1章 §1.2 过程规范、§1.4 软件生命周期标准；第3章 §3.2 组织过程定义；第9章 §9.1 过程模型的剪裁。

### 第15题 保证过程一致性与可重复性的措施

**题目**：在建立软件过程中，为了确保过程的一致性和可重复性，应该采取什么措施（　）
A、为每个项目定制独特的过程
B、引入敏捷开发方法，灵活应对变化
C、标准化过程文档和模板
D、依赖开发团队的个人经验和技能

**参考答案：C** ✅

**解析**：过程的一致性与可重复性依赖**标准化**：把过程定义、活动、输入输出、角色职责、检查表、文档模板固化下来，任何人按同一套规范执行都能得到相似结果——这正是**组织级过程资产**（过程定义、模板、指南、经验库）的意义。
- A 每个项目各搞一套，过程无法沉淀，也谈不上可重复（正确做法是在标准过程基础上**裁剪**）。
- B 敏捷的灵活性不等于没有规范，敏捷同样强调迭代规范、工程实践与团队约定。
- D 依赖个人经验正是"不成熟过程"的典型特征（人一走，能力就消失）。

**教材对应**：第1章 §1.2 过程规范；第3章 §3.2 组织过程定义；第2章 §2.1 过程成熟度标准（不成熟过程的特点）。

### 第16题 需求不明确且需尽早上市时的模型选择（⚠️存疑题）

**题目**：在开发一个具体需求不明确且会发生变化，系统需要具有可扩充性，同时希望尽早投入市场的软件项目时，应该选择以下哪种软件过程模型（　）
A、瀑布模型　B、增量模型　C、螺旋模型　D、敏捷模型

**参考答案：B（增量模型）** ⚠️

**解析**：
- A 错：瀑布模型要求需求早期基本确定，且只有到最后阶段才有可运行产品，既不能应对需求变化，也不满足"尽早投入市场"。
- **B 增量模型（推荐答案）**：把系统划分为若干增量，先交付最重要的核心增量，使用户尽早拿到可用产品版本（满足"尽早投入市场"），后续增量逐步补充并适应新需求；同时它要求软件体系结构具有良好**可扩充性**，以便新增量顺利集成。题干"需要具有可扩充性"是增量模型的典型前提与特征，也是多数教材把该组合指向增量模型的原因。
- C 螺旋模型：以风险分析为核心，适合大型、复杂、高风险项目，对小型项目过程偏重；题干并未强调"高风险"。
- D 敏捷模型：确实最适合"需求不明确且经常变化"，通过短迭代、持续交付响应变化，也能尽早交付可用软件；**若把"需求不明确且会变化"作为首要判据，选 D 也有充分理由**。

**存疑说明**：B 与 D 都能自圆其说。判 B 的核心依据是"可扩充性 + 尽早投入市场"这两个增量模型关键词，且第 20 题已单独考查"需求不明确或经常变化"指向敏捷，为避免重复，本题更可能考增量模型；判 D 的依据是"需求不明确且会变化"是敏捷的典型场景。**应试建议**：选 B 并简述"增量可早期交付、架构可扩充"；若老师课件把敏捷列为标准答案，按 D 作答亦可，答题时点明理由即可。

**教材对应**：第1章 §1.5.1 软件过程模型；第10章 §10.3 敏捷模型的软件过程管理。

### 第17题 螺旋模型的描述辨析

**题目**：螺旋模型是软件开发中的一种迭代过程模型，它结合了瀑布模型和原型模型的元素，并强调了风险评估的重要性。关于螺旋模型，以下哪一项描述是不正确的（　）
A、螺旋模型是一种迭代模型，每个迭代都包括规划、风险分析、工程实施、评审四个基本活动。
B、螺旋模型适用于大型、复杂、高风险的项目，因为它能够不断地进行风险评估和管理。
C、螺旋模型在每个迭代结束时都会生成一个稳定的、可交付的产品版本。
D、螺旋模型不需要明确的用户需求就可以开始项目，因为它会在迭代过程中逐步明确需求。

**参考答案：C** ✅

**解析**：螺旋模型沿螺线每转一圈（一次迭代）依次经历四个象限：**制定计划 → 风险分析 → 实施工程 → 客户评估**。每个迭代结束时的产出通常是**原型或可运行的中间版本**，用于验证需求、降低风险；它并不承诺每轮都交付"稳定的、可交付的产品版本"——那是**增量模型**的特征（每个增量交付一组可用功能）。
- A、B 正确，是螺旋模型的标准描述。
- D 基本正确：螺旋模型以原型和风险分析为手段，允许在需求不很清晰时启动，并在迭代中逐步明确需求（这也是它与瀑布模型的重要区别）。

**易错点**：把"每轮交付可用版本"安到螺旋模型上，或把"风险分析"安到增量模型上，都是常见错误。

**教材对应**：第1章 §1.5.1 软件过程模型。

### 第18题 V 模型的描述辨析（⚠️存疑题）

**题目**：V 模型是软件开发中的常见模型，它与瀑布模型相比更强调测试的重要性，因此常用作软件测试模型。关于 V 模型，以下哪一项描述是不正确的（　）
A、V 模型中的测试活动与开发活动是并行进行的。
B、V 模型从需求分析阶段就开始考虑测试，确保每个开发阶段都有对应的测试阶段。
C、V 模型中的测试是逐步进行的，从单元测试到集成测试，再到系统测试，最后进行验收测试。
D、V 模型允许在项目的后期轻松地回溯到前面的开发阶段以修复发现的缺陷。

**参考答案：D** ⚠️（A 亦可判错）

**解析**：V 模型是瀑布模型的变体，左边是开发活动自上而下展开，右边是测试活动自下而上进行，两侧一一对应：
**需求分析 ↔ 验收测试；概要设计 ↔ 系统测试；详细设计 ↔ 集成测试；编码 ↔ 单元测试。**
- B 正确：V 模型的一大价值是测试计划与测试用例设计在需求、设计阶段就开始准备，每一开发阶段都有对应测试阶段。
- C 正确：测试自下而上逐级递进（单元 → 集成 → 系统 → 验收）。
- **D 不正确（最实质的错误项）**：V 模型整体是**串行**推进的，测试在编码完成后才执行，缺陷发现得晚；一旦在系统测试或验收测试阶段发现问题，需回溯到需求或设计阶段修改，代价高、影响面大。这正是 V 模型（以及瀑布模型）被反复批评的主要缺点，"后期轻松回溯修改"与事实完全相反。
- **A 也有问题（存疑点）**：V 模型本质串行，测试的执行发生在对应开发活动完成之后，并不是"测试活动与开发活动并行进行"；教材与主流测试资料通常把"测试与开发并行/同步、测试伴随整个开发周期"划归 **W 模型（双 V 模型）**。若严格按"并行属于 W 模型"的口径，A 同样是不正确的描述。

**存疑说明**：本题 A、D 在严格意义上都与 V 模型真实特征不符，属命题不严谨。
- 若命题意图是考查"V 模型的缺点（后期回溯代价高）"→ 选 **D**（V 模型串行、测试介入晚，是该模型最常被强调的局限，也是最不可能被误认为正确的表述）。
- 若命题意图是考查"V 模型与 W 模型（双 V 模型）的区别"→ 选 **A**（"测试与开发并行"是 W 模型的标志）。
- 从"三个选项必须为真"的命题逻辑看，作者更可能把"测试与开发并行"当作 V 模型的正面表述（部分资料确有"V 模型强调测试与开发同步推进"的说法），从而把 D 作为唯一错误项。**应试建议选 D**，并在答题时点一句 A 的争议。

**教材对应**：第1章 §1.5.1 软件过程模型；V 模型/W 模型的详细表述以课件为准。

### 第19题 增量模型的描述辨析

**题目**：增量模型是软件开发中的一种迭代过程模型。关于增量模型，以下哪一项描述是不正确的（　）
A、增量模型允许在项目的早期就交付部分功能给用户。
B、增量模型通过一系列迭代逐步构建和交付完整的软件系统。
C、增量模型每次迭代都从头开始重新设计、编码和测试整个系统。
D、增量模型有助于降低项目风险，因为可以逐步验证和确认系统的功能。

**参考答案：C** ✅

**解析**：增量模型把软件划分为若干增量，每个增量在已有体系结构基础上**新增**一部分功能并集成到系统中，用户反馈作用于后续增量，因此每次迭代是"在原有成果上累加"，而不是"推倒重来"。
- A、B、D 均为增量模型的正确描述：早期交付部分功能、逐步构建与交付、通过逐步验证降低风险。
- C 错得明确：每次迭代重做整个系统不是增量模型，更像"抛弃式原型"或无复用的重复开发，成本极高且与增量思想相悖。

**教材对应**：第1章 §1.5.1 软件过程模型。

### 第20题 适用于需求不明确或经常变化的模型

**题目**：以下哪个模型适用于需求不明确或经常变化的项目（　）
A、瀑布模型　B、敏捷模型　C、螺旋模型　D、V 模型

**参考答案：B** ✅

**解析**：敏捷模型以短周期迭代、持续交付可用软件、拥抱变化为核心价值观，通过频繁的客户反馈与重构应对需求的不确定性与变化，是"需求不明确或经常变化"最典型的适用模型。
- A 瀑布模型、D V 模型都要求需求早期基本确定，重文档、重顺序，对需求变化的适应能力差。
- C 螺旋模型也允许在需求不清时启动（靠原型与风险分析逐步明确需求），但它的强项是**大型、高风险**项目的风险管理，过程相对重型；若题目只问"需求不明确或经常变化"，首选敏捷。C 可视为次优可辩选项（见第 16 题解析）。

**教材对应**：第1章 §1.5.1 软件过程模型；第10章 §10.3 敏捷模型的软件过程管理。

## 二、简答题

### 简答题 1. 简述软件需求的三个层次

**答案：**

软件需求按"由粗到细、由业务到实现"划分为三个层次，三者自上而下逐层分解，并可双向追溯。

**（1）业务需求（Business Requirements）**
- 描述组织或客户**为什么要开发这个系统**，即系统应达成的业务目标。
- 关注高层价值：市场机会、竞争优势、降低成本、提高效率、满足法规与合规要求等。
- 典型载体：项目愿景与范围文档（Vision and Scope）。
- 主要读者：客户高层、投资与决策者、项目经理。

**（2）用户需求（User Requirements）**
- 描述**用户使用系统要完成什么任务**，即用户视角下的使用需求。
- 通常使用使用场景、用例（Use Case）、用户故事、任务描述等表示。
- 只说明"做什么"，不涉及内部实现细节。
- 主要读者：最终用户、需求分析人员、开发与测试人员。

**（3）系统需求（System Requirements）**
- 把用户需求细化、精确化为开发人员**可实现的规格说明**，是需求工程的最终产物。
- 包含两类：**功能需求**（系统必须提供的功能、输入输出、处理逻辑、异常处理、业务规则）与**非功能需求**（性能、可靠性、安全性、可用性、可维护性、接口约束、设计约束等）。
- 典型载体：软件需求规格说明书（SRS）、需求模型（用例图、类图、活动图等）、数据字典。
- 主要读者：设计、编码、测试与维护人员。

**三者关系**：业务需求 → 指导 → 用户需求 → 细化/派生 → 系统需求。上层需求是下层需求的来源与依据，下层需求必须能追溯到上层目标；上层目标一旦变更，应通过需求变更控制流程分析并调整下层需求，从而保证一致性。

**教材对应**：第4章 §4.2 需求开发（需求层次与需求类型）；§4.3 需求管理（需求追溯）。

### 简答题 2. 简述需求变更控制的一般流程

**答案：**

需求变更控制的目标不是禁止变更，而是使变更**有序、可控、可追溯**，其一般流程如下。

**（1）提出变更申请**：由用户、开发人员或其他干系人填写变更申请单，说明变更内容、理由、提出人、日期、紧急程度及期望完成时间，提交变更管理机构。

**（2）变更影响分析**：由需求分析人员或变更控制委员会（CCB）组织分析，内容包括：技术可行性与实现方案；对需求范围、需求基线的影响；对进度、成本、工作量、质量与风险的影响；涉及的配置项与各阶段工作产品；必要时给出工作量与工期估算。

**（3）评审与决策**：CCB 对变更进行评审并作出结论——批准、拒绝、推迟或补充材料后再议。批准时确定优先级、实现方案、实施时间与责任人，并形成书面记录。

**（4）变更实施**：修改需求规格说明书与相关需求模型，必要时建立新的需求基线；同步修改受影响的设计文档、源代码、测试用例、项目计划、合同、用户手册等工作产品，保持可追溯性。

**（5）验证与确认**：通过评审和测试验证变更是否正确、完整地实现，确认没有引入新缺陷，也没有破坏原有功能（回归测试）。

**（6）基线更新与配置管理**：将变更后的需求及相关工作产品纳入配置管理，更新版本号与需求基线，记录变更状态，做到可追溯、可审计。

**（7）通知与沟通**：将变更结果通知所有受影响的干系人，更新变更日志，并对变更进行跟踪直至闭环。

**要点**：建立需求基线；设立 CCB；变更必须"申请—分析—审批—实施—验证—归档"闭环；坚持版本控制与状态跟踪；防止需求随意蔓延（scope creep）。

**教材对应**：第4章 §4.3 需求管理；附录A §A.4 需求变更管理过程规范；第6章 §6.1 软件配置管理（基线、变更控制、状态记录）。

### 简答题 3. 依据 ISO/IEC 12207 简述基本过程、支持过程、组织过程的基本内容

**答案：**

ISO/IEC 12207《软件生存周期过程》为软件的获取、供应、开发、运行、维护等建立共同的过程框架。按经典划分（ISO/IEC 12207:1995），软件生存周期过程分为**基本过程、支持过程、组织过程**三类，共 17 个过程。

**一、基本过程（5 个）**——直接服务于软件产品的产生、使用与演进，是生存周期的主线。
1. **获取过程**：需方定义并获取满足需求的软件产品或服务，包括需求确定、招标、选择供方、签订合同、验收与交付管理。
2. **供应过程**：供方按合同提供软件产品或服务，包括投标、签订合同、制订项目计划、执行并交付。
3. **开发过程**：开发者把需求转化为软件产品，包括需求分析、体系结构设计、详细设计、编码、集成、测试、安装和验收支持。
4. **运行过程**：运行方在预定环境中使用软件，包括运行准备、运行测试、实际使用和运行支持。
5. **维护过程**：维护方对软件进行修改，包括问题分析、修改实现、评审、回归测试、版本升级与退役。

**二、支持过程（8 个）**——作为其他过程的组成部分被使用，起保证与辅助作用，使项目可控、产品可信。
1. **文档编制过程**：规定并编制生存周期各阶段所需的文档（计划、设计、开发、管理、产品文档）。
2. **配置管理过程**：对配置项进行标识、控制、状态记录与变更管理，保证完整性、一致性和可追溯性。
3. **质量保证过程**：为产品与过程符合规定要求和计划提供客观证据（质量策划、评审、检查、记录）。
4. **验证过程**：通过评审、测试等手段判断某阶段产物是否正确地实现了上一阶段的需求（是否"正确地构造产品"）。
5. **确认过程**：判断最终产品是否满足预期用途和用户需求（是否"构造了正确的产品"）。
6. **联合评审过程**：需方、供方等相关方共同对项目进展与产品进行评审，分为管理评审与技术评审。
7. **审核过程**：由独立于被审核方的第三方对产品、过程或活动进行审核，判断其是否符合合同、标准与计划。
8. **问题解决过程**：对开发、运行、维护中发现的问题进行分析、定位、处理并跟踪闭环，形成问题报告。

**三、组织过程（4 个）**——由组织建立并实施，为项目过程提供组织级的基础设施、管理与改进支撑。
1. **管理过程**：对过程进行策划、组织、监控与控制，包括项目计划、资源分配、进度与成本控制、风险管理与报告。
2. **基础设施过程**：建立并维护软件生存周期所需的基础设施，包括硬件、软件工具、网络、标准、方法和开发环境。
3. **改进过程**：对组织的过程进行评估、度量和持续改进，提高过程能力与产品质量。
4. **培训过程**：识别并提供人员培训，使人员具备完成任务所需的知识和技能。

**三类过程的关系**：基本过程面向产品（获取、开发、运行、维护），支持过程是保证产品质量与项目可控的手段，组织过程为前两类过程提供组织级支撑；三类过程通过过程的调用、反馈与并行执行相互联系，共同构成完整的软件生存周期过程框架。

**口径提示**：
- 本教材第1章 §1.3 把过程需求划分为**软件工程过程、软件支持过程、软件管理过程、软件组织过程、客户—供应商过程**五类，与 ISO/IEC 12207 的三分类是不同视角：工程过程对应开发/运行/维护，客户—供应商过程对应获取/供应，管理过程与组织过程被单独列出。
- ISO/IEC 12207:2008 改版后把过程重组为协议过程、组织级项目使能过程、技术管理过程、技术过程、软件实现过程、软件支持过程、软件复用过程等过程组；若课件采用新版口径，以课件为准。

**教材对应**：第1章 §1.3 软件生命周期的过程需求、§1.4 软件生命周期标准（§1.4.1 ISO/IEC 标准体系）。

### 简答题 4. 什么是软件过程

**答案：**

**（1）定义**：软件过程（software process）是人们用于开发和维护软件及其相关产品（项目计划、需求文档、设计文档、代码、测试用例、用户手册等）的一组相互关联的活动、方法、实践和变换。按 ISO/IEC 12207 的说法，过程是"把输入转化为输出的一组相互关联的活动"。

**（2）组成要素**：
1. **活动**：为达到某一目标而开展的工作，如需求分析、设计、编码、测试。
2. **任务**：活动之下可执行、可检查的最小工作单元。
3. **角色**：承担活动的人员或组织，如项目经理、需求分析人员、开发者、测试人员、配置管理员。
4. **资源与约束**：工具、方法、时间、成本、标准与规范。
5. **产物（工作产品）**：过程执行产生的中间产品与最终产品。

**（3）分类**：
- 按 ISO/IEC 12207 分为基本过程、支持过程、组织过程（本教材则分为工程、支持、管理、组织、客户—供应商过程）。
- 按过程定义的层次分为组织级标准过程、项目级裁剪过程、个人级过程（如 PSP/TSP）。
- 按生存周期的组织方式表现为各种过程模型：瀑布模型、V 模型、原型模型、增量模型、螺旋模型、RUP、敏捷过程等。

**（4）意义**：软件过程决定软件产品的质量与生产率。规范、可度量、可改进的过程能提高开发效率、降低成本与风险、保证软件质量；过程不稳定或缺乏管理，则容易出现进度失控、质量缺陷、返工与协作混乱。因此软件工程强调"以过程为中心"，通过**定义过程 → 执行过程 → 度量过程 → 改进过程**的闭环，持续提升组织的过程能力（成熟度等级、过程评估与改进都建立在这一基础上）。

**教材对应**：第1章 §1.1 软件过程（§1.1.1 过程、§1.1.2 软件过程的分类和组成、§1.1.3 软件过程定义的层次性）、§1.2 过程规范；第2章（过程成熟度）；第9章（过程评估和改进）。

## 三、情景题

### 情景题 1. "校园失物招领系统"学生团队的过程问题分析

**题目背景**：张三是软件工程专业的学生，他组织了一个 5 人团队开发一个"校园失物招领系统"。项目计划 2 个月完成，这是团队第一次正式合作开发软件项目。团队采取的工作方式：每个人自己负责一部分功能、没有统一的需求文档，只有口头沟通、代码保存在各自的电脑上，没有使用版本控制、测试是在自己电脑上简单试试、每周开一次会，但会议没有明确议程。团队目前碰到一些问题：组员 A 和组员 B 开发的功能接口对不上，需要大量修改、组员 C 改代码时不小心删除了组员 D 昨天写的功能、团队成员不清楚其他人的进展、已经完成的模块存在很多明显的 bug 但无法进行有效的跟踪和修正等等。大家对 2 个月能否完成项目似乎越来越没信心。

**请分析回答**：（1）列出当前团队在软件开发过程中存在的主要问题；（2）针对每个问题，说明它会带来什么具体的不良后果；（3）为什么团队需要建立规范的软件开发过程。

#### （1）当前团队在软件开发过程中存在的主要问题

**1. 需求管理缺失**
- 没有统一的需求文档，需求只存在于口头沟通和个人的理解中；
- 没有经过评审的需求基线与需求确认，也没有需求变更的记录与跟踪。

**2. 系统设计与接口定义缺失**
- 团队没有总体（体系结构）设计，没有划分模块边界；
- 模块之间的接口（数据格式、调用方式、错误处理约定）没有事先约定，每个人"各自为战"。

**3. 配置管理与版本控制缺失**
- 源代码保存在各自电脑上，没有使用 Git/SVN 等版本控制工具；
- 没有统一的代码仓库、没有基线、没有分支与合并策略，也没有备份机制。

**4. 集成机制缺失**
- 没有集成计划与集成时间点，"各写各的"，把集成留到最后；
- 没有持续集成、冒烟测试或接口联调机制。

**5. 测试与缺陷管理不规范**
- 测试只是"在自己电脑上简单试试"，没有测试计划、测试用例与测试记录；
- 没有缺陷（Bug）跟踪机制，缺陷的发现、分派、修复、验证状态无人记录。

**6. 项目计划与进度跟踪缺失**
- 没有工作分解结构（WBS）、任务分配、里程碑与交付物定义；
- 没有进度跟踪与状态报告机制，工作进展只存在于各人脑中。

**7. 沟通与会议管理无效**
- 每周开会但无议程、无记录、无决议跟踪、无责任人；
- 缺少日常沟通机制与信息共享渠道。

**8. 角色与职责不明确**
- 5 人团队没有明确划分项目经理/组长、需求、设计、配置管理、测试、质量保证等角色；
- 关键过程活动（需求管理、配置管理、测试）无人负责。

**9. 质量保证与风险管理缺位**
- 没有质量目标、评审活动与质量标准；
- 团队首次合作、缺乏经验，却没有识别风险（进度风险、人员风险、技术风险）和应对措施。

#### （2）每个问题带来的具体不良后果

**1. 需求管理缺失 →** 各人对功能理解不一致，做出来的东西与用户（学校、同学）预期不符；需求遗漏或不断"加码"（需求蔓延）；没有需求基线，无法判断项目是否完成、无法验收；后期发现偏差时已投入大量工作，返工代价极高。

**2. 设计与接口未定义 →** A 与 B 开发的功能接口对不上，双方的数据结构、参数、返回值、异常处理都不一致，必须大量修改甚至重写；集成阶段问题集中爆发，形成"集成地狱"，团队把大量时间花在修补衔接上而不是实现功能。

**3. 无版本控制 →** C 修改代码时误删 D 的成果，无法恢复，也查不出是谁、在哪一步删除的；无法回溯历史版本，出现"昨天还能跑、今天跑不起来"却无从定位；无法并行开发与合并，容易互相覆盖；个人电脑损坏或误操作会直接造成成果永久丢失。

**4. 集成机制缺失 →** 各模块单独看都能运行，合在一起就工作不了；接口不一致的问题到项目末期才暴露，此时修正成本最高，直接冲击 2 个月的工期目标。

**5. 测试与缺陷管理不规范 →** 已完成模块存在大量明显 Bug，却没人记录、分派和跟踪，导致缺陷反复出现、重复报告、遗漏修复；无法判断哪些功能真正"完成"，质量状态不可见；交付用户后问题集中暴露，返工与信任损失更大。

**6. 计划与进度跟踪缺失 →** 团队成员不清楚其他人的进展，容易出现重复劳动或"三不管"任务；无法评估剩余工作量，也无法预测能否按期完成；问题被一再拖延，直到最后才发现来不及，团队信心不断下降。

**7. 会议无效 →** 会上讨论的问题没有结论、没有责任人、没有截止时间，议而不决、决而不行；同样的问题反复开会讨论，问题不断积压；会议占用时间却产生不了推进项目的成果。

**8. 角色与职责不清 →** 出现问题时互相推诿、无人负责；需求、配置管理、测试等关键工作没有归属，容易被忽视；协作摩擦增多，团队士气下降。

**9. 质量保证与风险管理缺位 →** 缺陷只能事后靠运气发现；一旦出现成员退出、课程冲突、技术方案失败、需求变化等风险，团队没有预案，只能被动应对，项目随时可能崩盘。

**总体后果**：过程失控导致**质量、进度、成本三者同时恶化**——接口返工、代码丢失、缺陷无法收敛、进度不可见，最终"2 个月能否完成"从计划问题变成信心问题。

#### （3）为什么团队需要建立规范的软件开发过程

**1. 软件过程是把输入转化为输出的一组相互关联的活动。** 只有把这些活动定义清楚——谁做、做什么、按什么顺序、用什么方法、产出什么、达到什么标准——工作才能从"靠个人随意发挥"变成**可重复、可预测、可度量、可改进**的行为。这正是 CMM/CMMI、ISO/IEC 12207 等标准强调过程管理的根本原因。

**2. 软件是多人协作的产物，协作必须以规范的过程为基础。** 多人协作至少需要三个共同基础：**共同的需求基线**（大家做的是同一个东西）、**统一的接口约定**（各自部分能拼在一起）、**共享的配置库**（成果不丢失、可并行、可回溯）。缺少任何一项，A/B 接口对不上、C 删掉 D 的代码这类问题就会反复发生；团队规模越大，沟通与集成成本越高。

**3. 质量主要由过程保证，而不是靠事后测试补救。** 规范的需求评审、设计评审、代码规范、单元测试与配置管理能在早期发现并拦截缺陷。缺陷发现得越晚，修复成本越高（需求阶段的一个错误如果到验收测试才被发现，可能要改设计、改代码、重做测试）。规范过程就是把"质量"内建到每个活动中。

**4. 规范过程是项目可控、可预测的前提。** 通过工作分解、任务分配、里程碑、进度跟踪与状态报告，团队才能知道"谁在做什么、做到哪一步、还剩多少工作、卡在哪里"，从而对"2 个月能否完成"作出真实判断，并及时调整范围或计划，而不是等到最后才发现来不及。

**5. 规范过程便于知识沉淀与人员交接。** 文档、版本库、缺陷记录、会议纪要使项目知识不再依赖某个人的电脑或记忆；成员请假、退出或课程冲突时，工作仍可继续，风险大大降低。

**6. 规范过程支持持续改进。** 过程可度量之后，团队才能发现薄弱环节（集成太晚、缺陷修复慢等），有针对性地调整流程，逐步提高过程能力、生产率和产品质量——这就是"定义—执行—度量—改进"的闭环。

**7. 对首次正式合作的学生团队尤为关键。** 本案例的根本问题不是能力不足，而是缺少最基本的工程规范。团队至少应做到：
- 形成需求文档并组织评审，明确范围与优先级，管住变更；
- 做总体设计，明确模块划分与**接口约定**；
- 使用 Git 等版本控制工具，建立共享仓库与提交规范；
- 建立缺陷记录与跟踪（哪怕是一张共享的缺陷表）；
- 制定简单计划，明确任务、责任人和里程碑，定期跟踪进度与风险；
- 会议设议程、做记录、明确决议与责任人并跟踪落实；
- 明确角色分工（组长/项目管理、需求、配置管理、测试等）。

**结论**：团队当前的核心症结不在技术，而在**没有规范的软件过程**。过程决定协作方式，协作方式决定产品质量与项目成败。先建立并执行最基本的规范过程，把需求、接口、版本、缺陷、计划和沟通管起来，才能把"越来越没信心"转变为可管理、可预测的项目，保证在 2 个月内按期、按质地完成校园失物招领系统。
