## 1.1–1.5 端系统、互联网核心与交换方式

课件用**连通性**和**资源共享**概括网络的作用。各校选手访问同一入口体现连通性，集中使用题库、评测算力和榜单体现资源共享。选手电脑、云主机和独立评测机都是端系统，属于互联网的**边缘部分**。校园出口、运营商网络和云网络中的路由设备为分组提供转发服务，体现**核心部分**的作用。机房内可按覆盖范围称为 LAN，跨校连接经广域网完成。LAN、MAN、WAN是覆盖范围的分类。

**C/S 与 P2P**描述端系统通信方式。浏览器是提交请求的客户端，OJ 主服务接收请求。独立评测机主动连接 OJ 时，也可在该连接上扮演客户端。P2P 的对等端可以互相提供资源，例如节点交换各自已经拥有的文件分块。复习互联网演进时，记住从早期网络到多网络互联，再到 ISP 互联。IXP 让网络运营者直接交换部分流量。RFC 是发布互联网技术文档的系列，其中有标准轨道文档，也有其他类别。

联赛可以采用下面的部署，其中代理、主服务和评测组件可按实际部署合并或拆开。各校数据汇总入口和数据格式由主办方约定。 [Hydro 官方维护文档](https://hydro.js.org/zh/docs/Hydro/system/maintain)

```text
选手浏览器 ── HTTPS ──> 云端反向代理 ──> HydroOJ 主服务 ──> 数据库
                                             ↕
                                           评测机
各校汇总脚本 ── HTTPS ──> 主办方约定的上传入口
```

| 交换方式 | 教材里的处理单位或资源 | 套进测试数据上传 |
| --- | --- | --- |
| 电路交换 | 先建立通路，通信期间占用已预留资源 | 通道建好后可连续传，空闲时间也会占用它 |
| 报文交换 | 存储转发完整报文 | 中继收完一整份测试包才向下一站转发 |
| 分组交换 | 给报文分段并加首部，逐分组存储转发 | 中继送走第一组时，源端可以继续发送第二组 |

分组交换有利于统计共享和流水传输，会引入首部、排队和缓存管理开销。分组交换与是否建立连接是两个角度。IP可逐个转发数据报，端系统同时可以在它上面运行面向连接的TCP。

## 1.6 四类时延怎么分

| 指标 | 算法或含义 | 题目里容易忽略的量 |
| --- | --- | --- |
| 发送时延 | `L/R`，把 `L` bit 全部推入速率为 `R` 的链路 | `L` 可能包含各组首部，`R` 用 bit/s |
| 传播时延 | `d/v`，信号走过距离 `d` 的耗时 | 千米先转米，`v` 是传播速度 |
| 处理时延 | 分析首部、校验或查表的耗时 | 按题目说明计入 |
| 排队时延 | 等候输出链路空闲的耗时 | 随缓存、负载和突发而变化 |
| 吞吐量 | 单位时间实际通过的数据量 | 应用有效吞吐量只统计有效数据 |
| 时延带宽积 | 链路带宽乘单程传播时延，单位通常为 bit | 估算窗口时常用带宽乘 RTT，口径不同 |
| RTT | 一次往返的耗时 | 题设 RTT、Ping 测量和 HTTP 完整响应的起止点要分别看 |

链路利用率接近饱和时，突发流量更容易造成排队。联赛开场的网页延迟与判题等待也可能同时升高。服务器的排队、编译、运行测试和更新榜单都消耗时间，选手看到的总等待由这些环节共同组成。课件中的非性能指标还包括可靠性、可扩展性、可管理性和成本。

### 例题 1｜期中第1题变式：两段速率不同，还有首部

A 经一个存储转发节点向云端发送 `490 000 B`。500 组，每组载荷 `980 B`、首部 `20 B`。两段链路速率为 `16、8 Mbit/s`，距离为 `120、240 km`，传播速度均为 `2 × 10⁸ m/s`。源端连续发送，两段链路可独立工作，缓存充足且无其他流量，忽略处理和丢包。从第一比特开始计时，求首组和最后一组完整到达的时间。

**第一步，算每组实际发送的比特数。** `(980 + 20) × 8 = 8000 bit`。链路要发送首部，所以两段发送时延分别为 `8000/(16×10⁶)=0.5 ms` 和 `8000/(8×10⁶)=1 ms`。两段传播时延分别是 `120000/(2×10⁸)=0.6 ms` 和 `1.2 ms`。

**第二步，追首组的最后一个比特。** `t=0.5 ms` 时，最后一个比特刚从 A 进入第一段。再过 `0.6 ms`，中继完整收到第一组，此时才可向第二段发送。最后一个比特经第二段发送与传播，在 `0.5+0.6+1+1.2=3.3 ms` 到达终点。

**第三步，找流水线的出组间隔。** 第一段每 `0.5 ms` 送来一组，第二段每 `1 ms` 才能送完一组，故终点每 `1 ms` 完整收到一组。首组已经计入，剩下 `499` 个间隔，总耗时 `3.3+499×1=502.3 ms`。

```text
同样假设下，n 个等长分组通过 k 条独立链路：
首组时间 = Σ(各段发送时延 + 各段传播时延)
全文件时间 = 首组时间 + (n - 1) × 最大单段发送时延
等速时，纯发送项化简为 (n + k - 1) × L/R
```

拿掉流水条件、让分组长度不同、增加链路共享或每组等待确认，都需要重画时序。若题目另说应用测得用时 `4 s`，有效吞吐量为 `490000×8/4=0.98 Mbit/s`，此处只计文件正文。

## 1.7 五层体系结构与一次提交

| 层 | 常见数据单位 | 联赛中的角色 |
| --- | --- | --- |
| 应用层 | 报文 | HTTP 表达提交代码、登录和查询榜单 |
| 运输层 | TCP 报文段或 UDP 用户数据报 | 用端口区分进程。TCP提供可靠、有序的字节流 |
| 网络层 | IP 数据报 | 按目的 IP 跨网络逐跳转发 |
| 数据链路层 | 帧 | 负责当前链路上的交付，例如以太网 MAC 转发 |
| 物理层 | 比特 | 通过电、光或无线信号传送比特 |

源端逐层封装，目的端逐层解释首部。普通路由器剥掉当前链路的帧，处理 IP 首部并按下一跳链路重新成帧。OSI 模型有七层，教材还介绍 TCP/IP 的四层表达。五层模型单列物理层和数据链路层，便于跟课件做题。

**协议**约定对等实体之间的交互，语法管格式，语义管动作与含义，同步管先后顺序。**服务**描述下层能为相邻上层提供什么。**服务访问点**是相邻层交换信息的逻辑位置。一个层如何提供服务，可以在接口约定保持稳定的前提下替换。

## 联赛实践 如何衡量“提交卡住”

1. 记录 DNS、建连、首字节和完整响应耗时，确认网页请求在哪一步变慢。
2. 对照提交创建、评测开始、评测完成的服务器时间，区分排队和实际运行。
3. 若后台结果已产生，页面需要手动刷新，检查自动更新通道。Hydro 的代理文档说明 WebSocket 代理设置会影响评测状态刷新。 [Hydro 反向代理文档](https://hydro.js.org/docs/Hydro/install/proxy)

跨校汇总可给每份数据设一个由比赛、学校和版本组成的批次标识。服务端收齐后核对文件大小和来自可信清单的 SHA-256，持久化或导入完成再返回批次状态。超时后可查询原批次，再按同一标识重试，避免生成重复记录。TCP确认的是字节交付，比赛端仍要定义“哪一版数据已成功入库”。

## 自测与详解

1. **三段链路。** 在例题的存储转发和流水条件下改为80组，每组1500 B，链路速率12、6、24 Mbit/s，传播时延1、0.5、2 ms。先算每组12000 bit，三段发送时延为1、2、0.5 ms。首组 `1+2+0.5+1+0.5+2=7 ms`。输出间隔由6 Mbit/s的链路决定，末组 `7+79×2=165 ms`。
2. **单程与往返。** 100 Mbit/s，单程传播 20 ms，实测 RTT 为 40 ms。单程链路在途量 `100×10⁶×0.020=2 Mbit`，即 250 000 B。若按所测 RTT 估算支撑同一吞吐量的窗口，乘 `0.040` 得 500 000 B。两者都要除以 8 才得到字节。
